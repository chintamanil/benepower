System Design

Architecture — Multimodal Multi-Agent RAG

Members and providers reach the same brain through three doors — chat, image upload, and a live phone call. The phone path bridges Twilio → LiveKit SIP; a multi-tenant Operator dispatcher resolves the inbound number to the right partner and spawns a specialist agent, which grounds answers in a Bedrock knowledge base, captures structured state, and writes everything back to a HIPAA-compliant backend.

What it does

Answers benefits questions, grounded

Turns "what's my deductible?" or "is this CPT covered?" into a retrieval-grounded, cited answer — plan docs, accumulators, eligibility, and provider networks — instead of a human reading policy PDFs on every call.

Who uses it

Members & providers, at scale

HIPAA-verified members self-serve enrollment, claims, and ID-card questions; providers verify eligibility and precertification — across a multi-tenant backend serving 1.2M+ onboarded users.

Why an operator + specialist agents, not one big prompt
Isolation

Per-persona behavior

Each agent carries its own prompt, tools, and guardrails: Member answers are plain-language (URAC level), Provider answers are technical and concise, and Intake is a single-purpose 7-state capture machine with no free-form Q&A.

Grounding

Retrieval before generation

The Member/Provider agents call Bedrock Knowledge Base RetrieveAndGenerate (one KB per plan/document set) and return in-line citations — S3 source, page, chunk — so no claim floats free of its source.

Memory

Bounded, hand-off-safe context

Chat context is summarized before it blows past Bedrock token limits (max_items 50 · keep_last_turns 5) and filtered across agent hand-offs, so the next agent inherits what the caller already said without re-asking.

Trust & Reliability

A RAG Evaluation Framework That Gates Deploys

An agent that talks to patients about their coverage cannot ship on vibes.

  • Every call, today: creates a ticket with a summary and a structured JSON record built from the transcript (CSAT score, confidence and more).
  • Pipeline: an Airflow (MWAA) pipeline processes each record. When the first pass isn’t confident, it re-runs the call with a stronger model (Sonnet 5.5, escalating to Opus 5.5) to build a detailed per-ticket object.
  • Reporting: Marimo notebooks turn that data into internal metrics and the KPI reports customers see (Customer Pulse ↗).
  • Release gating: a 3-layer RAG evaluation harness on Bedrock + RAGAS scores a golden set and blocks deployment when a gate fails.
  • After the gate: a reference-ticket QA harness compares baseline and variant offline. Live per-call splits are planned (A/B testing ↗).

Three Layers of Evaluation

A call where every individual turn scores well can still be a compliance failure if the turns happen in the wrong order. Three complementary layers each catch a different class of failure.

Layer 1 · Deterministic

Fast, reproducible, no LLM

Pure-Python rules: field-capture rate & accuracy, branching accuracy, ASR robustness on hard inputs, turn-count efficiency, and latency — sub-second and 100% repeatable.

Layer 2 · LLM-as-Judge

RAGAS on Bedrock Claude

Faithfulness, response relevancy, answer correctness, context precision/recall, topic adherence, tool-call accuracy, and semantic similarity — judged in-account so PHI never leaves AWS.

Layer 3 · Phase-Level

Healthcare compliance

Structural checks turn-level metrics miss: identity before data, branch detection before branch questions, no premature disclosure, and call termination on HIPAA failure.

Two Evaluation Systems, Different Jobs

There are two separate evaluation layers on this platform, and they are easy to conflate.

  • Release gate: asks "is the agent good enough to ship?" and blocks a release when the answer is no.
  • Customer Pulse: asks "did the agent actually finish the job for real callers?" and steers the program.
  • What differs: inputs, cadence and consequence.
  • What they share: no metric appears in both.

Production hardening · detail
Config resolution

TTS is per-agent and per-stage

The concierge runs ElevenLabs eleven_turbo_v2_5; the intake agent runs AWS Polly generative ("Ruth", 16 kHz) in prod and preprod, and ElevenLabs only in beta. One provider key, deep-merged per stage — and that divergence is exactly what hid a P0 from every environment developers test in (deep dive).

Naturalness

VAD & turn detection

Silero VAD plus LiveKit's MultilingualModel turn detector stop the agent being cut off by "hmm" / "I see," keep RAG answers interruptible, and prevent double-speak via a shared response mixin.

Stability

STT session isolation

ResilientAWSSTT wraps AWS Transcribe with a unique session-id per agent (and a fresh one for the supervisor during transfer), and retries a failed stream a bounded number of times with a fresh session — so a caller reading a chart in silence doesn't leave the agent deaf.

Accuracy

ID read-back

Member IDs and reference numbers are read back with an Apple-Boy-Charlie phonetic alphabet (NATO disallowed), per-digit pacing, and pronunciation normalization (HIPAA → "hip pah") — and ticket reference numbers are spelled out by code, not left to the model to read.

Compliance

HIPAA hard gate

No PHI is collected before verification succeeds; a scripted refusal after repeated failed attempts, with the ticket's hipaa_verification_status set to VERIFIED on success and caller-ID kept separate from member verification.

Continuity

Warm transfer

Escalations use a consultation-room model: Sally briefs a supervisor privately (≤15s), dials the skill queue by DTMF, then merges audio into the caller's room — recording and transcript attached to the ticket.

Approach

Included in the denominator

Calls we were on the hook for

Any call classified as intake intent where the member was resolvable and the caller stayed on the line to do the work. If we failed one of these, that is our miss and it counts against us.

Quality Gate · Beta

From Pass/Fail to IQ

The six-gate eval answers “is this build safe to ship?” with pass or fail. The TruVo IQ score answers a harder question for the FDHN-powered agent: how much of what members actually ask can it resolve, plan by plan? It is expressed on the human IQ scale so the number is legible to a client, and it is explicitly a scoreboard — it exists to drive the next piece of work.

IQ  =  round( 100 + ( RR − 0.80 ) × 150 )
RR (resolution rate) = ( autonomous + 0.5 × partial ) ÷ TAM. 80% resolution is IQ 100; every 10 points of resolution moves the score 15 — one standard deviation.
TAM (total addressable market) is the full universe of member question categories. A category the agent cannot answer yet still counts in the denominator, at zero. SAM removes categories the client confirmed out of scope at onboarding, so the board can show both: the member’s experience (TAM) and the agent’s accountability (SAM).

Approach
  • Honest scoring. A response that deflects is a redirect even though the agent said something. “All questions returned an answer” is not a pass.
  • Scored per plan option. Each benefit option within a group is graded on its own, because members ask about their plan, not the average of the group’s plans.
  • Bands: 130+ Exceptional · 115–129 Superior · 100–114 Competent · 85–99 Developing · 70–84 Limited · below 70 Impaired.

The production gate checks the minimum, never the average. The overall score is the weakest plan option, and the release rule is that an agent must reach Competent (IQ 100) on every plan option before it goes to production. One strong plan cannot carry a weak one through. The rule is blunt on purpose: we don’t release agents that cannot reliably find a member’s path to care.

Six-gate RAG eval

Is the build safe?

Offline gates over a curated golden set — deterministic checks, RAGAS judges, phase compliance. A single FAIL out of six blocks the release.

Customer Pulse · v2

Is production working?

Every live call scored and bucketed against the North Star, with the tiered LLM-as-judge adding the semantic checks.

TruVo IQ

How capable is this agent, per plan?

Sits before release for the FDHN-powered agent: a question battery run against each plan option, graded, rolled up to one number the gate can enforce.

All three use the same discipline — deterministic math over graded inputs, a published formula, and a threshold that drives action: the two gates block a release, Customer Pulse resets priorities. They differ in what they judge: the build, the live call, and the plan-by-plan capability of the agent.

Experimentation

Did the Change Actually Help?

Passing the release gate and finishing the job don’t answer the question every prompt, model or voice change raises: is this version better than the last one?

  • Before: a change was judged by the next nightly eval run.

One Symptom, Four Different Owners

Early triage was consistently wrong, and wrong in an expensive way — we kept tuning prompts for bugs that lived in the EDI builder. Approach
  • Refuse to triage from the transcript alone — the recording answers a question it cannot.
  • Read the transcript as two streams — what the caller said, and what the agent itself said — not as one conversation.

Layer 1 · Speech In

STT — Speech Is a Search Key, Not a Data Source

The instinct is to make transcription more accurate. That is mostly a losing battle on a phone line with a provider reading a chart. The winning move was to stop treating the transcript as data and start treating it as a lossy key into a database that already holds the correct value — then make every consumer of that key tolerant.

Approach
  • Wrap the vendor stream in a retry loop rather than tuning silence tolerance — the silence is legitimate.
  • Rotate the session ID to a fresh UUID before every reconnect; reusing the prior request identifier is unsafe. This is the 1.3 behavior; on 1.8.9 the plugin restarts the idle timeout itself on the same session, and the wrapper stays as a bounded 3-retry safety net.
  • Swallow one known plugin UnboundLocalError raised during shutdown; re-raise everything else.

On a precert call, 15 seconds of silence is normal — the caller is reading a chart. The stock plugin surfaced the timeout as a hard stream failure, so the agent simply stopped hearing the caller mid-call.

Cost & Latency

Paying for the Prompt Once, Not Every Turn

A voice agent re-sends its entire system prompt and tool schema on every single turn — an ~86-turn call pays for the same ~900-line state machine eighty-six times. Two changes fixed most of that bill, and a third moved the accounting itself out of the agent.

0.1×Cache-read rate vs. standard input
1.25×Cache-write premium, paid once per call
2Cached segments — system prompt + tool schemas
0Cache writes on one-shot calls — summaries stay uncached
0Agent redeploys when a price changes
every callCache hit ratio emitted, not assumed
Approach
  • Cache the two segments that never change within a call — the system prompt and the tool schemas — so each turn pays full rate only on the conversational delta.
  • Make it a config flag, opted into at the long-lived call sites — the session LLM and the RAG LLM — so one-shot calls never pay a cache write they will not read back.
  • Measure the hit ratio per call and ship it as telemetry — a cache you don't measure is a cache you assume is working.
  • Emit raw token counts from the agent and apply pricing downstream, so a rate change is a pipeline edit and old calls can be re-costed retroactively.

The economics are lopsided enough to make this the single highest-leverage change: a cache read bills at a tenth of a standard input token, against a one-time write premium of 1.25×. The break-even is roughly two turns — every real call clears it long before the caller finishes spelling their member ID.

Rule 1

Never let survival work compete on ROI

Compliance and security have no upside — they only avoid death. Scored on return they lose every time, and every time they should have won. Take them off the board first, then prioritize what's left.

Rule 2

Proof value is real and gets underweighted

Engineers discount it as "not real work". A credible number is often the sentence that raises the round or closes the logo — which makes it, at a startup, frequently the highest-leverage thing available.

Applied herePublishing the KPI's denominator wasn't a feature. It was the artifact that made the number arguable-with, and that's what moved the traffic ramp.

The regime switch is the actual skill. Run large-company process at a startup and you sound bureaucratic — charter analysis for a call three people could make in a hallway. Run startup speed logic at a large company and you sound reckless — "we'll rewrite it later" about a system with three hundred dependent teams. Either failure reads as incompetence from the other side.

The triggers that flip you back: a second team could plausibly own it · external consumers with expectations · the first enterprise or compliance contract · the cost of being wrong exceeds the cost of deciding carefully · the thing outlives the person who built it. And the discount only ever applied to things you can throw away — anything load-bearing (data model, authz, tenancy, money movement, anything regulated) gets full rigor at any stage.
