System Design

Architecture — Multimodal Multi-Agent RAG

Members and providers reach the same brain through three doors — chat, image upload, and a live phone call. The phone path bridges Twilio → LiveKit SIP; a multi-tenant Operator dispatcher resolves the inbound number to the right partner and spawns a specialist agent, which grounds answers in a Bedrock knowledge base, captures structured state, and writes everything back to a HIPAA-compliant backend.

What it does

Answers benefits questions, grounded

Turns "what's my deductible?" or "is this CPT covered?" into a retrieval-grounded, cited answer — plan docs, accumulators, eligibility, and provider networks — instead of a human reading policy PDFs on every call.

Who uses it

Members & providers, at scale

HIPAA-verified members self-serve enrollment, claims, and ID-card questions; providers verify eligibility and precertification — across a multi-tenant backend serving hundreds of thousands of onboarded users.

Why an operator + specialist agents, not one big prompt
Isolation

Per-persona behavior

Each agent carries its own prompt, tools, and guardrails: Member answers are plain-language (URAC level), Provider answers are technical and concise, and Intake is a single-purpose 7-state capture machine with no free-form Q&A.

Grounding

Retrieval before generation

The Member/Provider agents call Bedrock Knowledge Base RetrieveAndGenerate (one KB per plan/document set) and return in-line citations — S3 source, page, chunk — so no claim floats free of its source.

Memory

Bounded, hand-off-safe context

Chat context is summarized before it blows past Bedrock token limits (max_items 50 · keep_last_turns 5) and filtered across agent hand-offs, so the next agent inherits what the caller already said without re-asking.

Three Layers of Evaluation

A call where every individual turn scores well can still be a compliance failure if the turns happen in the wrong order. Three complementary layers each catch a different class of failure.

Layer 1 · Deterministic

Fast, reproducible, no LLM

Pure-Python rules: field-capture rate & accuracy, branching accuracy, ASR robustness on hard inputs, turn-count efficiency, and latency — sub-second and 100% repeatable.

Layer 2 · LLM-as-Judge

RAGAS on Bedrock Claude

Faithfulness, response relevancy, answer correctness, context precision/recall, topic adherence, tool-call accuracy, and semantic similarity — judged in-account so PHI never leaves AWS.

Layer 3 · Phase-Level

Healthcare compliance

Structural checks turn-level metrics miss: identity before data, branch detection before branch questions, no premature disclosure, and call termination on HIPAA failure.

Production-Hardening I Drove
Config resolution

TTS is per-agent and per-stage

The concierge runs ElevenLabs eleven_turbo_v2_5; the intake agent runs AWS Polly generative ("Ruth", 16 kHz) in prod and preprod, and ElevenLabs only in beta. One provider key, deep-merged per stage — and that divergence is exactly what hid a P0 from every environment developers test in (deep dive).

Naturalness

VAD & turn detection

Silero VAD plus LiveKit's MultilingualModel turn detector stop the agent being cut off by "hmm" / "I see," keep RAG answers interruptible, and prevent double-speak via a shared response mixin.

Stability

STT session isolation

ResilientAWSSTT wraps AWS Transcribe with a unique session-id per agent (and a fresh one for the supervisor during transfer) — killing the silent STT failures that AWS session-id collisions used to cause.

Accuracy

ID read-back

Member IDs and reference numbers are read back with an Apple-Boy-Charlie phonetic alphabet (NATO disallowed), per-digit pacing, and pronunciation normalization (HIPAA → "hip pah") — eliminating ASR failures on repeated digits.

Compliance

HIPAA hard gate

No PHI is collected before verification succeeds; 3-strike retry then a scripted refusal, with the ticket's hipaa_verified flag patched on success and caller-ID kept separate from member verification.

Continuity

Warm transfer

Escalations use a consultation-room model: Sally briefs a supervisor privately (≤15s), dials the skill queue by DTMF, then merges audio into the caller's room — recording and transcript attached to the ticket.

The North Star

The Metric the Program Steers By

The dashboard tracks two dozen metrics; most of them exist to explain movement in this one. It's deliberately the hardest to hit, because it only counts calls that produced a real, delivered EDI artifact — and its formula, denominator, and exclusions are all published below.

North Star  =  EDI files delivered  ÷  eligible intake calls
Numerator — a ticket whose status reached INTAKE_DELIVERED: the X12 278 was generated, transmitted, and acknowledged by the payer. Not "ticket created". Not "intake attempted". Delivered.
Denominator — calls where the caller genuinely attempted an intake and we had what we needed to serve them. Calls we could never have completed are excluded, and the exclusion list is fixed and published.

Approach
  • Keep two rates on one numerator rather than picking the flattering denominator and defending it.
  • Print them adjacent — the smaller denominator is only credible while the bigger one sits next to it.

Deflection counts every call that reached the line, including ones no agent could have converted; the North Star drops those by design. Same 10k EDIs, two honest readings.

Included in the denominator

Calls we were on the hook for

Any call classified as intake intent where the member was resolvable and the caller stayed on the line to do the work. If we failed one of these, that is our miss and it counts against us.

Why it's built this wayInflating the denominator with unwinnable calls makes the number look bad and gets it ignored; shrinking it with excuses makes the number look good and gets it distrusted. Fixing the list in code, and printing it, kills both moves.
Excluded — and why

Calls no agent could convert

Six fixed exclusions, evaluated per call from the deterministic pipeline's unverified_reason:

The Organizing Insight

One Symptom, Four Different Owners

Early triage was consistently wrong, and wrong in an expensive way — we kept tuning prompts for bugs that lived in the EDI builder. Every caller-visible failure arrives as the same sentence: "Sally couldn't verify the member." That sentence is compatible with at least four unrelated root causes in four different files owned by different people.

Approach
  • Refuse to triage from the transcript alone — the recording answers a question it cannot.
  • Read the transcript as two streams — what the caller said, and what the agent itself said — not as one conversation.
  • Make the first triage step a single yes/no that eliminates three of four layers before anyone opens a file.

The transcript is not what the caller heard.

The transcript is what the speech engine believed on the way in, and what the model generated on the way out. The recording is what the caller actually heard. Those two disagree more often than you would expect — and the disagreement, plus which side of the transcript it sits on, is the diagnosis.

Layer 1 · Speech In

STT — Speech Is a Search Key, Not a Data Source

The instinct is to make transcription more accurate. That is mostly a losing battle on a phone line with a provider reading a chart. The winning move was to stop treating the transcript as data and start treating it as a lossy key into a database that already holds the correct value — then make every consumer of that key tolerant.

Cost & Latency

Paying for the Prompt Once, Not Every Turn

A voice agent re-sends its entire system prompt and tool schema on every single turn — a 30-turn call pays for the same ~900-line state machine thirty times. Two changes fixed most of that bill, and a third moved the accounting itself out of the agent.

0.1×Cache-read rate vs. standard input
1.25×Cache-write premium, paid once per call
2Cached segments — system prompt + tool schemas
3Summary calls sharing one cached prefix
0Agent redeploys when a price changes
every callCache hit ratio emitted, not assumed
Approach
  • Cache the two segments that never change within a call — the system prompt and the tool schemas — so each turn pays full rate only on the conversational delta.
  • Enable it on the client factory, not per call site, so every agent, background job and the QA caller inherits it and nobody can forget.
  • Measure the hit ratio per call and ship it as telemetry — a cache you don't measure is a cache you assume is working.
  • Emit raw token counts from the agent and apply pricing downstream, so a rate change is a pipeline edit and old calls can be re-costed retroactively.

The economics are lopsided enough to make this the single highest-leverage change: a cache read bills at a tenth of a standard input token, against a one-time write premium of 1.25×. The break-even is roughly two turns — every real call clears it long before the caller finishes spelling their member ID.

The Defect the Cost Work Found
P0 · caller-facing TTS config

Polly was reading the markup out loud

46.93sSynthesis with markup spoken as words
10.15sSame utterance, TextType=ssml
5Words Polly emits for one <break/> tag
1 branchWired for ElevenLabs, not for Polly
Approach
  • The normalizer emits <break time="250ms"/> between digits so a member ID is intelligible. aws.TTS() was constructed with no text_type, so Polly defaulted to text and vocalized the tag: "break time equals 250 milliseconds."
  • The same function's ElevenLabs branch already threaded the flag. One provider branch inside a single if/else was wired and the other was not — so the fix is a parity change, not a feature.
  • Ship the <speak> wrapper and the config flag in one commit, because reverting the flag alone lands on a worse cell.

It could not happen where anyone tested. Beta runs ElevenLabs; preprod and prod run Polly. The defect lived exclusively in the environments developers never dial into — which is why a cost investigation, not a bug report, is what surfaced it.

Cross-finding · the fix fed the bill

The markup was re-entering the model's context

~10Tokens of markup per digit spoken back
2Call sites that write to chat_ctx
every turnContext re-sent to Bedrock thereafter
1 argumentTwo uses of one string — that was the bug
Approach
  • say() normalized the text first, then passed the normalized string to both synthesis and add_to_chat_ctx. So the <break/> tags entered conversation history, were re-sent to Bedrock on every subsequent turn, and were persisted into the conversation log.
  • Fix: pass un-normalized text to the context and normalized text only to the synthesizer. The two arguments should never have been the same string.
  • Land it before capturing any replay baseline — a baseline recorded while the defect is live encodes the defect as the expected output.

This is the finding I care about most: enabling the speech fix would have inflated the exact tokens the cost work exists to reduce, and it also changes the bytes a record-fidelity baseline is defined over. Correctness, cost and verifiability turned out to be one defect, and none of the three original write-ups named it.

Critical · caught by mechanical sweep

The fix would have silenced the test harness

Approach
  • The plan said "apply text_type="ssml" to all four aws.TTS sites," and the acceptance criterion was a grep proving all four had it.
  • The fourth site is the QA caller — the harness that phones the agent to test it. It has no normalizer, so it emits no markup; declaring plain text as SSML makes Polly reject every request. It goes mute.
  • Correct precondition is "does this site sit behind the normalizer?" — never "is this site in the grep output?" The exclusion is now enforced by a test, not a comment.

The acceptance criterion did not merely permit the defect — it mandated it, and the oracle would have reported success. And the thing being broken was the regression suite that would have caught it. Found by cross-referencing every call site against whether its module reaches the normalizer; not by re-reading the plan, which had already confirmed the error twice.

Approach
  • Roughly twenty tests asserted <break/> tags were the expected output and passed happily under the live defect. Zero tests covered the boundary where the defect actually lived.

The written record said 12 failures. The measured value was 18. Capturing a baseline from prose rather than from a run would have seeded the oracle with a wrong expected set and passed while six failures went unaccounted for.

The 5-Whys — Where It Stopped Being a Bug
The 278 was quarantined because the subscriber's date of birth was an empty string, failing the pipeline's validator.
The agent uploaded empty subscriber fields because the subscriber lookup failed to find the primary policyholder.
The lookup hit a support-search endpoint that returned 502 Bad Gateway.
That endpoint uses a contains match across the full unscoped member table — a LIKE '%…%' query over ~956K rows — so it timed out.
The contains approach was inherited from the admin search UI pattern. For this lookup the ID is already canonical, so an exact match would return instantly.
There is no exact-match endpoint for this ID, because the filter set does not declare the field — and the query parameter is therefore silently ignored, returning all org-scoped members regardless of the filter value.
The agent has no retry logic for this lookup. A single transient 502 permanently loses the data, and the "graceful degradation" assumes the caller can supply subscriber info — but on intake calls, providers are never asked for the insured's demographics.

The finding that made this worth writing up. Chasing why 6 to 8 expected results came back as tens of thousands, we found the filter had never been applied. Every call logged the same result count regardless of the value searched for:

the same number, every call, every value
Searching members: external_id='…0012' → 57549 results
Searching members: external_id='…001'  → 57549 results
Searching members: external_id='…00'   → 57549 results
Progressive trim exhausted → falls through to DOB + name → succeeds

Verification had only ever worked because a different tier — name + DOB, on a different endpoint that filters correctly — was silently carrying every call. The member-ID verification path had never functioned since launch. It looked healthy because the fallback always caught it, while adding roughly 6 seconds of latency to every single call. The P0 fix wasn't an optimization; it restored a path that had never worked.

Rule 1

Never let survival work compete on ROI

Compliance and security have no upside — they only avoid death. Scored on return they lose every time, and every time they should have won. Take them off the board first, then prioritize what's left.

Applied hereThe HIPAA gate, the 3-factor rule and the fail-closed escalation were never ranked against feature work. That's why they shipped.
Rule 2

Proof value is real and gets underweighted

Engineers discount it as "not real work". A credible number is often the sentence that raises the round or closes the logo — which makes it, at a startup, frequently the highest-leverage thing available.
